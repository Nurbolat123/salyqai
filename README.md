# Salyq AI — бэкенд

ИИ-бухгалтер для ИП на упрощённом режиме (форма 910.00) в Казахстане. Техническое
задание — [`docs/spec.md`](docs/spec.md).
Стек: Python 3.12, FastAPI, SQLAlchemy 2, PostgreSQL 16.

Сейчас реализованы:

| Модуль | Пакет | Раздел ТЗ | Что делает |
|---|---|---|---|
| Вход, согласия, журнал | `salyq/auth` | 2, 4.1, 6 | Вход по ЭЦП (подпись одноразового nonce), сессии, три типа согласий с версиями, журнал действий только на добавление |
| Налоговый движок | `salyq/tax` | 4.4 | Налог за полугодие по ставкам регионов, соцплатежи ИП за себя, лимит режима, сроки. Суммы в тиынах, параметры из конфигурации по годам, «след» расчёта |
| Шлюз обезличивания | `salyq/privacy` | 2, 6 | Единственный путь текста к внешней LLM: проверка согласия, удаление ПДн, суммы диапазонами, блокировка при остатках ПДн |
| Импорт выписок | `salyq/statements` | 4.2 | Выписка Kaspi Business (PDF, XLSX, CSV), дедупликация, шифрование ПДн в БД |

## Запуск

```bash
docker compose up --build          # миграции + API на http://localhost:8000, документация — /docs
docker compose run --rm tests      # все тесты, включая прогон на реальном PostgreSQL
```

Локально без Docker:

```bash
python3.12 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
pytest                                             # тесты с PostgreSQL пропускаются
TEST_DATABASE_URL=postgresql+psycopg://salyq:salyq@localhost:5432/salyq_test pytest
cp .env.example .env                               # заполнить ключи шифрования
alembic upgrade head                               # схема БД
uvicorn salyq.main:app --reload
```

| DELETE | `/api/v1/auth/session` | Выход |
| GET / PATCH | `/api/v1/me` | Профиль ИП: регион (КАТО), ОКЭД, дата регистрации, работники |
| GET / POST | `/api/v1/consents` | Список согласий и актуальных версий / дать согласие `{type, version}` |
| DELETE | `/api/v1/consents/{type}` | Отозвать согласие |
| GET | `/api/v1/tax/years` | Годы, для которых есть конфигурация |

ответ 403 с `{"code": "CONSENT_REQUIRED", "consent": …, "version": …}`. Калькуляторы

curl -s localhost:8000/api/v1/tax/simplified -H 'content-type: application/json' \

разметки и подтверждения операций.

## Вход, согласия, журнал действий

**Вход по ЭЦП** (ТЗ 4.1):

1. Приложение получает одноразовый nonce: `POST /auth/ecp/challenge`.
2. Пользователь подписывает его в NCALayer или eGov Mobile.
3. Приложение отправляет подпись: `POST /auth/ecp`.

Сервер проверяет подпись и берёт ИИН и ФИО из сертификата. При первом входе создаётся
пользователь. Nonce одноразовый, в том числе после неудачной попытки. В БД хранятся
только хеши nonce и токена сессии, а ИИН и ФИО — зашифрованными (поиск по слепому индексу
`iin_hash`).

Проверка подписи спрятана за интерфейсом `EcpVerifier` (`salyq/auth/ecp.py`):

- `SALYQ_ECP_VERIFIER=dev` — заглушка **без криптографии**: `signed_data` — base64 от JSON
  `{nonce, iin, full_name}`, подписать можно через `DevEcpVerifier.sign(...)`. При
  `SALYQ_ENVIRONMENT=prod` приложение с ней не запустится.
- `SALYQ_ECP_VERIFIER=ncanode` — проверка CMS-подписи через NCANode. Пока не реализована:
  нужен доступ к тестовому контуру eGov и тестовые ключи НУЦ.

**Согласия** (ТЗ 2, 4.1): `pd_processing` (обязательное), `automated_processing`
(ст. 19-1, понадобится для авторазметки), `cross_border` (необязательное). Версии текстов
задаёт `CONSENT_VERSIONS` в `salyq/auth/consents.py`. Если выходит новая редакция текста,
старое согласие перестаёт действовать, и пользователь соглашается заново. Отзыв проставляет
`revoked_at`, история сохраняется.

**Журнал действий** (`audit_log`) пишется в той же транзакции, что и само действие.
Записываются события: вход, неудачный вход с причиной, выход, выдача и отзыв согласия,
изменение профиля, загрузка выписки. В `details` попадают только коды и идентификаторы,
без ПДн. В PostgreSQL изменять и удалять записи запрещает триггер.

**Счета принадлежат пользователю.** Один и тот же IBAN у двух пользователей — это два
разных счёта, и дедупликация между ними не смешивается.

## Миграции

Схему БД меняют только миграции Alembic (`migrations/`). Приложение таблицы не создаёт.

```bash
alembic upgrade head                                   # применить
alembic revision --autogenerate -m "что изменилось"    # после правки salyq/models.py
alembic check                                          # модели и миграции совпадают?
```

Колонки с шифртекстом в миграциях объявлены как `sa.Text()`: так миграции не зависят от
кода приложения. Тесты на PostgreSQL строят схему из миграций, а не через `create_all`, и
отдельно проверяют три вещи: схема совпадает с моделями, откат до `base` работает,
журнал защищён от изменений.

## Налоговый движок

**Деньги.** Все суммы хранятся в тиынах (`int`, 1 ₸ = 100 тиын), `float` на входе запрещён
(`salyq/money.py`). Умножение на ставку округляется до тиына по правилу half-up.
Суммы к уплате округляются до целых тенге.

**Конфигурация по годам** (`salyq/tax/rates/<год>.yaml`). В файле года хранятся:

- МРП и МЗП;
- базовая ставка и допустимый диапазон ставок маслихатов;
- распределение налога между ИПН и СН;
- лимит режима и ступени предупреждений;
- порог по НДС;
- ставки и базы соцплатежей;
- сроки сдачи и уплаты: смещение от конца полугодия или месяца.

При загрузке файл проверяется pydantic-схемой. В «след» записываются год, версия и sha256
файла.

Изменения утверждает эксперт (ТЗ 4.4): он заполняет `approved_by`. Пока поле пустое,
каждый расчёт возвращает предупреждение `CONFIG_NOT_APPROVED`. Сейчас конфигурация хранится
в YAML в репозитории. Таблица `tax_config` с редактированием из админ-панели — следующий шаг.

**Регионы.** Ставка маслихата берётся из справочника `region_rates`: регион (КАТО), ОКЭД,
ставка, дата начала действия, ссылка на решение. Действует ставка на конец периода; ставка
для конкретного ОКЭД важнее общей по региону. Если в справочнике ставки нет, применяется
базовая с предупреждением `REGION_RATE_MISSING`. При доходе в нескольких регионах налог
считается раздельно и складывается.

**Лимит.** В 2026 году лимит составляет 600 000 МРП = 2 595 000 000 ₸ за полугодие.
Предупреждения:

- `INCOME_LIMIT_50`, `INCOME_LIMIT_80`, `INCOME_LIMIT_95` — достигнута доля лимита;
- `INCOME_LIMIT_EXCEEDED` — лимит превышен;
- `VAT_THRESHOLD_EXCEEDED` — годовой порог по НДС превышен (выход за рамки MVP).

**«След».** В нём записаны:

- конфигурация: год, версия, sha256, `approved_by`;
- операции, вошедшие в доход (`RegionIncome.from_items`);
- каждый шаг: формула, входные значения, результат в тиынах и в тенге.

По следу строится экран «Как посчитано».

> ⚠️ Параметры 2025 и 2026 годов заполнены по открытым источникам и не утверждены.
> По ТЗ (раздел 7) бухгалтер должен подтвердить ставки и базы соцплатежей 2026 года и
> сроки 910.00 по новому НК. Сейчас в конфигурации стоят сроки по прежнему НК:
> сдача — 15-е, уплата — 25-е число второго месяца после полугодия.

## Шлюз обезличивания

```python
from salyq.privacy import Anonymizer, prepare_external

a = Anonymizer(known_names=["Иванов Иван"])   # имена из профиля и контрагентов
safe = prepare_external(prompt, a, cross_border_consent=user.has_cross_border_consent)
answer = a.deanonymize(llm_answer)            # подставить исходные значения обратно
```

`prepare_external` выполняет три шага:

1. Без согласия на трансграничную передачу выбрасывает `ConsentRequired`: запрос нужно
   направить в локальную модель.
2. Заменяет данные на токены: ИИН, БИН, IBAN, карты, телефоны, e-mail, ФИО, адреса
   (`[PERSON_1]`, `[ADDRESS_1]`). Суммы заменяет диапазонами, например
   `[СУММА В ТЕНГЕ: 100 тыс.–500 тыс.]`; диапазоны обратно не восстанавливаются.
3. Проверяет остатки. Остаточная проверка грубее основных детекторов: она ищет 10 и более
   цифр подряд, префикс `KZ` с цифрами и символ `@`. При срабатывании выбрасывает
   `PIILeakError`, и запрос блокируется.

Принцип — лучше замаскировать лишнее, чем пропустить данные:

- любое 12-значное число маскируется. Тип ИИН или БИН определяется по контрольному разряду и структуре;
- номера карт, в том числе маскированные, маскируются без проверки по алгоритму Луна.

ФИО распознаются в нескольких видах:

- по русским и казахским отчествам (-ович, -овна, -ұлы, -қызы, «улы» отдельным словом);
- по инициалам;
- по контексту («ИП …», «получатель: …»);
- по списку `known_names`.

Адреса распознаются по маркерам «ул.», «пр.», «мкр.», «көшесі», «даңғылы» и другим, вместе
с номером дома и квартиры.

Ограничения: не распознаются имя без отчества и без контекста посреди фразы и адрес без
маркера («Абая 150»). Поэтому ФИО владельца и контрагентов нужно передавать в
`known_names`.

## Импорт выписок

Реестр парсеров по банкам — `salyq.statements.PARSERS`. Сейчас реализован `kaspi`; Halyk и
Freedom — следующими.

**Kaspi Business:**

- Форматы: PDF (таблицы через pdfplumber, шапка — текст над первой таблицей), XLSX и CSV
  (UTF-8 или cp1251).
- Колонки определяются по синонимам (`COLUMN_ALIASES`). Суммы поддерживаются в двух видах:
  раздельные «Дебет/Кредит» или одна колонка «Сумма» со знаком.
- Номер счёта и период берутся из шапки выписки. Если периода в шапке нет, он считается по
  датам операций.
- Строки, которые не удалось разобрать, не прерывают импорт. Они возвращаются в `skipped`
  с номером строки и причиной.
- Повтор заголовка на каждой странице PDF и итоговые строки пропускаются.

**Дедупликация** (ТЗ 4.2: банк, дата, сумма, референс):

- **С референсом** (номер документа) ключ = банк + счёт + дата + направление + валюта +
  сумма + референс. От назначения платежа и наименований ключ не зависит, поэтому PDF и
  XLSX за один период дублей не дают, даже если в PDF назначение обрезано.
- **Без референса** (например, продажи Kaspi QR) ключ строится по содержимому строки
  плюс порядковому номеру среди одинаковых строк файла. Две одинаковые продажи сохраняются
  обе, а повторная загрузка ничего не добавляет. Ограничение: если группа таких операций
  разрезана между двумя файлами посреди дня, возможен лишний дубль.
- Ключ хранится как HMAC-SHA256 в `transactions.fingerprint`. На пару
  `(account_id, fingerprint)` стоит уникальное ограничение, вставка идёт через
  `INSERT … ON CONFLICT DO NOTHING`.

## Хранение персональных данных

По разделу 6 ТЗ ПДн шифруются на уровне полей: AES-256-GCM, тип колонки `EncryptedText`
(`salyq/crypto.py`). Шифруются:

- IBAN счёта;
- наименование, ИИН/БИН и счёт контрагента;
- назначение платежа;
- имя загруженного файла.

Для поиска используются «слепые» индексы — HMAC с отдельным ключом: `iban_hash` и
`counterparty_hash` (по нему будут работать персональные правила разметки). Для показа
хранится `iban_masked` (`KZ18…5678`).

Ключи задаются переменными `SALYQ_FIELD_KEY` и `SALYQ_HMAC_KEY` (base64 от 32 байт). В
`docker-compose.yml` стоят ключи только для разработки; в проде ключи выдаёт KMS / Vault в
РК. Соответствие криптографии СТ РК 1073-2007 нужно уточнить у юриста (ТЗ, раздел 6).
